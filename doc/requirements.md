# Requirements and acceptance

What DaServer must be, and how each requirement is checked before a change is accepted. Every release candidate
goes through the checklist at the end; the results (numbers, test counts) are recorded in [roadmap.md](roadmap.md).

## 1. Product requirements

| # | Requirement | Acceptance |
|---|---|---|
| R0 | **General-purpose framework.** DaServer is a general ECS distributed server framework for high performance and high concurrency. It covers what every real-time backend needs (actors, services, messaging, membership, placement, persistence, ingress, client connections) and contains no business domain (logins, maps, matchmaking, inventories); capabilities sit in their own namespaces on public feature points, off unless configured. | `ArchitectureTests.TheRuntimeDoesNotDependOnClientConnections`: runtime folders use no `DaServer.Clients` type; domain code only under `samples/`. |
| R1 | **Business code only.** Users write messages, components, actors and services as static classes of `[Handle]` methods, and ECS systems. Registration, routing, serialization, placement, discovery and orchestration are generated or provided. (target, roadmap W2 and W3) Actor types are `IActor<T>` with `[Handles<K>]` classes of `[On<T>]` methods and `[UpdateInGroup<K>]` systems; the one generated `Registration.Create()` is the only registration, and a node's Program.cs stays about five lines (draft §0). | The sample server contains no registration list, no routing code, no serializer calls, no configuration strings for topology. |
| R2 | **One vocabulary, no hidden meaning.** A message is a `[NinoType, Message]` struct (`IRequest<TReply>` when answered; `[FromClient]`/`[ToClient]` say whether clients send it or receive it; plain `[NinoType]` types are data inside messages), handled by `[Handle]` methods; the message type decides the handler, the actor id (whose type names the actor type) is a call parameter; wire data is `[NinoType]`; ECS is EasyEcs. `[NinoFormerName]` only resolves a reported collision or keeps a renamed type's identity (its stored records). (target, roadmap W2) Messages are `[NinoType]` record structs whose interface says the flow: `IFromClient`/`IFromClient<R>` and `IToClient` (clients), `IMessageTo<K>`/`IRequestTo<K, R>` with `[From<K>]` (servers), `IEvent` (local); `[To]`, `[Latest]`, `[Once]`, `[From<K>]` and `[MaxReplySize(n)]` are the only message attributes (draft §4, §8). | README vocabulary table covers every attribute; analyzer reports every misuse (R10). |
| R3 | **No hard-coded topology.** No role strings. A node hosts what its process contains; the deployment unit is a project. Accepting clients is a capability (the `DaServer:Clients` section), not a role. (target, roadmap W5) Accepting clients is hosting the `Connection` actor type (`[Hosts<Connection>]`); a server type hosts what its `[Hosts<K>]` attributes name (draft §2). | `grep` finds no role names in `src/`, `samples/`; the AppHost declares node groups by project type only. |
| R4 | **Stateful and stateless.** Actors with typed ids (one loaded actor per id, on demand, rendezvous placement, one message at a time with each handler run to completion) and stateless services (load-balanced, local first). Handlers never wait: an ask's answer is mail, so actors that ask each other, in a chain or a cycle, always complete. (target, roadmap W4 and W6) Everything one sender sends to one target (messages, requests, answers, presence notices) arrives in send order (exceptions: ADR-096), sends to different targets never wait on each other, and a large message delays another pair by at most one fragment (ADR-096). A handler that calls `root.Commit()` has its root written at the next tick end and its output held until that write lands (ADR-097): an answer given after a commit survives a crash; a `[Once]` request that moves value runs exactly once by framework-assigned sequence numbers, its reply stored on the receiver until the sender's cumulative acknowledgement and the sender remembered until it is deleted (TCP's scheme without a time-based TIME-WAIT, ADR-099), and `AskUntilAnswered` asks it again after a crash until answered (ADR-100); actors keep running meanwhile. State is written asynchronously at tick ends through the store contract (ADR-102), one batch per 512 roots (and a byte cap on records), one guarded write per root (its record and row changes together, nothing across roots), at most `Store:WritesInFlight` in flight per world (plain changes at each root's staggered checkpoint instant, oldest unsaved first): a graceful exit writes everything within its stop budget and logs what it could not, and loses the unwritten changes of a root whose state does not serialize or whose row the store refuses (it keeps its last record, logged as `RecordUnwritable`); a crash loses the larger of the last interval and the write backlog's drain time (`daserver.store.oldest_unsaved_age`), except such a root, which loses everything since its last good record, and on a store below `Strict` also what a failover or crash of the store loses, which is not reported (ADR-082, ADR-097, ADR-104). | Cluster tests: single loaded actor per id across nodes, rebalance on join/leave without losing calls, service load balancing, chains and cycles of asks across nodes and through services (`CallChainTests`). |
| R5 | **Discovery and failure handling.** Nodes find each other through seeds and gossip; failed nodes are suspected and removed; graceful leave drains and unloads actors; a dropped node connection resumes without losing or repeating messages; a request whose caller already timed out is not run (on any node). Dispatch queues and mailboxes are bounded and refuse with `Overloaded` (renamed `Busy` with a `RetryAfter` in W4; target: every actor's mailbox is bounded on its own, so a hot actor refuses only its own mail, and an answer's room is reserved when its ask is made). (target, roadmap W6) Membership is a table in the store (Orleans' protocol, ADR-082), kept as one versioned document through the same store contract as records (ADR-103) on a store whose effective class is `Strict` (membership has no opt-in below it): nodes find each other there, without seeds; a failed node is declared dead by suspicion votes and a node that reads itself dead stops; a node whose isolation lease (`IsolationTimeout` from issuing its last read that showed it `Active`) runs out freezes its worlds (connections kept, mail queued in bounded queues), answers probes `Isolated` and resumes when it reads itself `Active`, or exits after `IsolationExit` when only it cannot reach the store, so a store outage longer than the lease pauses the whole cluster; a dead node keeps its slots, answered `Unavailable`, until they move after `dead_seen_at + IsolationTimeout + DeathMargin` on the store's clock; a node without a store starts only with `SingleNode` (and never with both), and a cluster of more than one node needs the store, gateways included. | Cluster tests for join, crash (dead after timeout), graceful leave with in-flight calls, connections dropped mid-stream (`LinkTests`), expired requests (local and across nodes), full mailboxes; (W6) `JoinWritesJoiningThenActive`, `SuspicionVotesDeclareDeath`, `DeclaredDeadNodeStopsItself`, `PartitionMinoritySideDeclaredDead`, `TableCasConflictRetries`, `StoreOutageFreezesAndResumes`, `ReplacementWaitsDeadSeenAtPlusIsolation`, `IsolatedNodeReachingPeersExitsAfterIsolationExit`, `StorelessWithoutSingleNodeRefusesStart`, `MembershipRequiresStrict`, `MembershipRegressionStopsTheNode`. |
| R6 | **Messages + ECS.** `Ask` (request/response), `Send` (one-way) and `Publish` (every service type handling the message) without naming the receiver's type; per-tick logic in EasyEcs systems of the world. (target, roadmap W) `Publish` is deleted; pub/sub between actors is the optional `DaServer.Topics` (W6b, ADR-090). | Tests cover each delivery kind (`EventTests`); the sample uses `Ask` and `Send`. |
| R7 | **Clients.** Many client-facing nodes behind one well-known address (the platform's load balancer; old connections move to new nodes, `MaxConnectionAge`; target, roadmap W5: only a node above its group's average sheds its excess, ADR-089); client messages validated by `[FromClient]`; session-bound actor ids; pushes to a session or a group serialized once and fanned out per client-facing node; `SessionClosed` delivered to bound and granted actors, also when a client-facing node crashes. (target, roadmap W5, ADR-095) A client cannot create actors or store rows by inventing keys (a `[To]` message reaches only keys with a record unless the type declares `[ActivatedBy]`; `CanCreate` validates before any row is written (a key that already has a record still activates); types that persist nothing write nothing; records claimed and never written expire), cannot name another user (key fields from the token's claims), and a client request that must not run twice is marked `[Once]`: the SDK resends it under the same call id until answered or for at most `ResumeWindow` from its first attempt, through other gateways included, every gateway enforcing that deadline, and the receiver runs it once and keeps the reply until the client acknowledges or the call's deadline has passed; a session is a gateway-signed token with a sliding end that every gateway refuses past, so an ended session cannot replay old calls through another gateway (ADR-099). Client packages load in a Godot 4 .NET game (`net10.0`); Unity is future work (ADR-086). A slow client is conflated and resynchronized before it is disconnected, and a push lost on the way marks its presence for a resync (ADR-096). | Gateway tests: server-only messages refused, binding isolation, group broadcast across client-facing nodes, exact delivery under churn, connections moving to a node started later, `SessionClosed` on close and crash; (target) `ClientToUnknownKeyIsNoActorAndWritesNothing`, `RouteFromClaimsIgnoresClientUser`, `OnceClientPurchaseResentRunsOnce`, `SessionTokenRefusedPastTByAnyGateway`, `ClientCallResendWindowEnforcedByGateway`, `ClientPackagesLoadOnNet10`. |
| R8 | **Orchestration.** One Aspire AppHost runs the cluster locally (dashboard, OpenTelemetry) and publishes it (Docker Compose / Kubernetes). Node projects carry no names, ports or seeds. | `tests/DaServer.E2E` starts the AppHost with `Aspire.Hosting.Testing` in CI and passes only when the bot exits 0 (`E2E OK`). |
| R9 | **ECS all the way down.** Business code and the shard runtime follow EasyEcs's ECS principles: actors are entities (`ActorKey`), behaviour is stateless static handlers and systems, per-actor runtime state (lifecycle, mailbox, known sessions) is components and tags, per-shard state is singletons, each runtime system has one job, no event bus inside a world, no inheritance or virtual members in user code (ADR-081). (target, roadmap W1 and W2, ADR-082) An actor is a root entity with its subtree in its type's world; presences, waiting asks, delayed events and reminders are child entities (`AskUntilAnswered`'s asks are store rows of the root, target); handlers are EasyEcs single-entity jobs and systems are `[ForEach]` methods on EasyEcs 4.7. | Design review against [EasyEcs ecs-principles](https://github.com/JasonXuDeveloper/EasyEcs/blob/master/doc/ecs-principles.md); no EECS warnings. |
| R10 | **Misuse is a build error** (warnings where §13 says so). Handler shapes (a static class, a static non-generic method, the message first, then only components, singletons, `Entity`, `World` and `Context`, no components in a service, the return type vs. the request's reply, no `async`, duplicates, accessibility), message shapes (struct, `[NinoType, Message]`, non-generic), types that cannot cross the wire, id collisions, messages used against their flow, actors, services and systems with fields, a session or group asked or addressed by a client, shared logic referencing the server, synchronous waits and work started on other threads in shard code, systems that ask, components declared beside logic, invalid persisted or handed-off components, `IPlaced` on a type that is not an actor id, a wire layout changed against its committed manifest or not recorded, a collection held directly by a client message, an actor disconnecting a session with `Send`, a misshapen `[Filter]`, a component parameter used after a structural change of its entity (DAS001-DAS022). (target, roadmap W3) The checks of draft §13 with ids DAS023–DAS034 (`[Latest]` misuse, `Commit`/`[Once]`/`AskUntilAnswered` on unsaved roots or from senders that cannot commit, `[Once]` written wrong, sending after `root.Delete()` returned `Ok`, an ask in a loop among them) and the kept DAS001–022 applied to the new API; retired ids are never reused. | One generator test case per diagnostic; generators never report diagnostics themselves. |
| R11 | **Scale.** 10,000 players through 3 gateways to one game node, moving in one map (area of interest, dead reckoning) while the realm broadcasts to everyone every 5 ticks: no gap, no disconnect, p99 broadcast latency under 250 ms on a 4-core machine, servers allocate nothing in steady state. | `dotnet run --project samples/mmo/Sample.AppHost` (its bots: `--bots 10000 --seconds 60 --lean`, broadcast p99 limit 250 ms) ends with the bots exiting 0; node stats lines show 0 KB/s without OTLP. |
| R12 | **Hot update without disconnecting clients.** (target, roadmap W6, ADR-084, ADR-098) A node changes its code (JIT or Native AOT alike) by handing its worlds and listening sockets to a warm standby over a local pipe: clients stay connected, nothing is lost, the old process resumes in place on any failure; layout or framework changes the handover cannot carry go through records or a rolling upgrade. | BenchmarkDotNet `HandoverPause` at 100,000 and 1,000,000 actors under JIT and AOT (recorded); `HotRestartKeepsClientsConnected`, `FailedHandoverResumesInPlace`; the E2E scenario hot-restarts a map node during the 10k-bot run without a disconnect. |
| R13 | **Released output and durability, by store class.** (target, roadmap W6 and W12, ADR-101, ADR-104) A store provider declares a durability class (`Strict`, `Replicated`, `Local`); the effective class is the lower of the declaration and the provider's self-check (at start and periodically), and a production node runs below `Strict` only when `DaServer:Store:AcceptDurability` (the Dashboard's store: `DaServer:Dashboard:AcceptDurability`) names that class, while membership always needs `Strict` and treats a version below one it held as a store fault that stops the node (development runs, those whose `IHostEnvironment.IsDevelopment()` is true, which `DaServer.Aspire` sets in run mode and never in what it publishes, and `TestCluster` exempt, with a warning; every other environment is production); the in-memory store holds records and the Dashboard's keys only in development and `TestCluster`, since any restart loses them, and a production node refuses it for them. `Strict`: what a `Commit` item sent leaves only once its write is durable under every failover the store performs, and an `Unknown` outcome releases nothing until `Confirm` shows the write (across the loss of any one database instance and any failover the store performs; the deployment's failure domain bounds it: three zones on Kubernetes, one host on Docker Compose, whose loss is not covered and which the start-up log line names. PostgreSQL: strict synchronous replication over two standbys with failover that never promotes a standby missing an acknowledged commit (`SafeFailover`: a quorum-aware tool, or manual promotion only on Compose), writes, claims and membership writes pausing rather than degrading (heartbeats skip and `DaServerMembershipWritePending` fires; nothing steps down), primary-only data sources, PostgreSQL 16 or later, `COMMIT` sent on its own and never cancelled); membership reads keep answering while a commit waits. Below `Strict` the guarantee is fencing only: two owners' writes never mix (a record's version is its fencing token); output leaves at the provider's replication wait, and a failover or crash may lose recent writes whose effects already left; the framework promises no detection of such a loss and reports only what it meets (a root's own token at an older generation; the node logs at start the class it accepted); `[Once]` and `AskUntilAnswered` hold except across such a loss. In every class a setting that can corrupt the store (PostgreSQL `fsync` or `full_page_writes` off) makes the class `Unsafe`: a fresh start stays not ready before it joins, and a serving node (or a hot restart's standby) goes on under the `Local` rules, with no class guarantee across a database host crash meanwhile, and alerts (`DaServerStoreUnsafe`; development and `TestCluster` exempt with a warning). | Conformance kit layer 4 per class (`UnknownReleasesOnlyAfterConfirm` with the primary up and the standby down, `RetriedWriteConfirmedBeforeRelease`, `ConfirmFindsWriteAbsentResends`, `TimedOutClaimConfirmedByRerun`, `MembershipWaitNeverTerminated`), `ConfirmNeverReleasesLaterItems`, `NonStrictStoreRefusedWithoutOptIn`, `SelfCheckLowersClass`, `MembershipRequiresStrict`, `DashboardStoreBelowStrictRefusedWithoutOptIn`, `OwnOlderVersionFencedAndCounted`, `UnsafeDurabilitySettingsDetected`, `UnsafeStoreDropsClassAndAlerts`, `UnsafeAtStartStaysNotReady`, `UnsafeDuringHotRestartTakesOver`, `InMemoryStoreRefusedForRecordsInProduction`, `ProductionIsAnyNonDevelopmentEnvironment`, `RolledBackEpochNeverMatchesOtherOwner`, `AbandonedBackendTerminatedBeforeRetry`, `TimedOutWriteNeverCancelled`, `MembershipReadsAnswerWhileCommitWaits`, `DataSourcesRequireReadWrite`, `PublishedStoreReplicatesSynchronously`. |

## 2. Engineering requirements

| # | Requirement | Acceptance |
|---|---|---|
| E1 | **Zero GC on hot paths** in steady state: calls, one-way messages, replies, events, pushes, broadcasts, mailbox, ECS ticks. | `AllocationTests` (process-wide counter, so background runtime work is included; any per-message allocation is >= 24 B; `BufferPool` growth to a new peak is pinned memory kept for reuse, counted apart and bounded): < 1 B per delivery for gateway fan-out; < 8 B per call/event across shards, across nodes and through a gateway to another node, per reply given later or after an ask, per delayed send, per checkpoint, per call of a 2,000-wide burst, per service message, per refusal (`Overloaded`, `Busy` in the target, `NotHosted`, relayed `Timeout`) and per actor load and unload; an idle node allocates nothing per tick or wake. BenchmarkDotNet `Allocated` per operation reported for RPC, events and broadcast (only harness allocations allowed, explained). |
| E2 | **Latency and throughput** measured with BenchmarkDotNet over real loopback sockets. | RPC round trip (same node, cross node), concurrent calls, events, group broadcast to 1k/5k clients, broadcast to everyone through 3 gateways (3k/9k): numbers recorded in the roadmap's release table (the README summarizes and links it); no regression > 10% against the previous recorded run without an explanation. |
| E3 | **Bounded memory.** Every queue and buffer is bounded or pooled; slow consumers are disconnected (target, roadmap W5: conflated first, the presence resynced, disconnected only after `Clients:SlowClientGrace`); pools retain at most a configured budget. One stated exception (target, ADR-100): while the store takes no data writes but still answers membership reads, nothing freezes, so a root's unwritten changes and asks grow in memory until the alert `DaServerStoreWritesBehind` is acted on; a full outage is bounded by the isolation freeze. | Code review checklist; `BufferPool` and connection limits documented next to the code. |
| E4 | **Thread safety is explicit.** User code runs on shard threads only; cross-thread handoff only through the shard dispatch queue; shared runtime state is immutable snapshots. | Review: no locks in user-facing code paths; every shared structure documents its contract. |
| E5 | **Decoupled layers.** Business code sees `ICluster` (messages, pushes, groups), never `Node`. Dependencies point one way. (target, roadmap W2) Six packages (ADR-086): Core → Client \| DaServer (the runtime and the node host) → the store providers (Persistence.PostgreSql; later Persistence.Redis and Persistence.MongoDb, ADR-102); Testing references DaServer and Client; Aspire is AppHost-side and references only Core, no server assembly. The optional packages (`DaServer.Reminders`, `DaServer.Topics`, `DaServer.Replication`, `DaServer.Dashboard`, ADR-090) reference DaServer (and Client where they have a client side) and nothing references them; the runtime never does. | `ArchitectureTests.PackagesDependOnlyDownwards` (the optional packages included); `Context.Cluster` and `world.Cluster` return `ICluster`. |
| E6 | **DRY and concise.** No copy-pasted variants (generated or shared helpers instead); no file over ~400 lines without a reason. | Review; `wc -l`. |
| E7 | **Incremental generator rules.** Syntax predicates first, equatable symbol-free models, tracking names, no diagnostics from generators. | `GeneratorTests.UnrelatedEditsHitTheCache` covers every syntax stage. |
| E8 | **Tests.** Unit, in-process cluster, gateway/client, generator/analyzer, allocation and end-to-end (AppHost + bots) tests; all green in CI on every push. | `dotnet test`: all pass; CI green. |
| E9 | **Docs.** README (what/why/how with mermaid), design, decisions (one ADR per non-obvious choice), roadmap, this file. Code, comments, commits and docs in English. | Review. |
| E10 | **Commits.** Logic, docs and CI in separate commits; author = repository owner, committer = signing identity (Verified); no session links. | GitHub shows Verified on every commit. |
| E11 | **Native AOT** (target, roadmap W8). Every node can publish with `PublishAot=true`, chosen per node (JIT images stay supported): registration, dispatch and framework systems are generated as closed types in the user's assembly (no reflection, `MakeGenericType`, `Activator` or assembly scanning); serialization is Nino's generated formatters; the HTTP plane uses the slim builder and no JSON in the framework (admin endpoints as Nino or plain text; JSON only per endpoint through the application's source-generated context, ADR-083). Framework projects set `IsAotCompatible` on their .NET targets (`net10.0` for the shared code, `net11.0` for the server core, ADR-086). JIT and AOT nodes change code the same way, by hot restart or rolling upgrade (ADR-084, ADR-098). | The trim and AOT analyzers run on every build (0 warnings, no suppression); release checklist step 6 publishes the samples' nodes with AOT. What holds and what remains to verify: [drafts/architecture.md](drafts/architecture.md) section 8. |

## 3. Release checklist

Run in order; record results in the roadmap.

1. `dotnet build DaServer.slnx` — 0 warnings, 0 errors.
2. `dotnet test DaServer.slnx` — all pass (count recorded).
3. `grep -rn "Role\|\"game\"\|\"gateway\"" src samples` — topology strings only in the AppHost (and doc comments).
4. BenchmarkDotNet: `RpcBenchmark`, `MessageBenchmark`, `BroadcastBenchmark`, `ScenarioBenchmark` — mean and
   allocated recorded.
5. Sample end to end: the AppHost's 10k-bot scenario prints `E2E OK` (R11).
6. Native AOT (E11; target, roadmap W8): `dotnet publish -p:PublishAot=true` for each sample node with 0 warnings, and the E2E tests
   passing against the AOT binaries.
7. Review against R0–R13 and E1–E11 (this file); open items go to the roadmap.
8. CI green on the pushed branch; commits Verified.
