# Requirements and acceptance

What DaServer must be, and how each requirement is checked before a change is accepted. Every release candidate
goes through the checklist at the end; the results (numbers, test counts) are recorded in [roadmap.md](roadmap.md).

## 1. Product requirements

| # | Requirement | Acceptance |
|---|---|---|
| R0 | **General-purpose framework.** DaServer is a general ECS distributed server framework for high performance and high concurrency. It covers what every real-time backend needs (actors, services, messaging, membership, placement, persistence, ingress, client connections) and contains no business domain (logins, maps, matchmaking, inventories); capabilities sit in their own namespaces on public feature points, off unless configured. | `ArchitectureTests.TheRuntimeDoesNotDependOnClientConnections`: runtime folders use no `DaServer.Clients` type; domain code only under `samples/`. |
| R1 | **Business code only.** Users write messages, components, actors and services as static classes of `[Handle]` methods, and ECS systems. Registration, routing, serialization, placement, discovery and orchestration are generated or provided. | The sample server contains no registration list, no routing code, no serializer calls, no configuration strings for topology. |
| R2 | **One vocabulary, no hidden meaning.** A message is a `[NinoType, Message]` struct (`IRequest<TReply>` when answered; `[FromClient]`/`[ToClient]` say whether clients send it or receive it; plain `[NinoType]` types are data inside messages), handled by `[Handle]` methods; the message type decides the handler, the actor id (whose type names the actor type) is a call parameter; wire data is `[NinoType]`; ECS is EasyEcs. `[NinoFormerName]` only resolves a reported collision or keeps a renamed type's identity (its stored records). | README vocabulary table covers every attribute; analyzer reports every misuse (R10). |
| R3 | **No hard-coded topology.** No role strings. A node hosts what its process contains; the deployment unit is a project. Accepting clients is a capability (the `DaServer:Clients` section), not a role. | `grep` finds no role names in `src/`, `samples/`; the AppHost declares node groups by project type only. |
| R4 | **Stateful and stateless.** Actors with typed ids (one loaded actor per id, on demand, rendezvous placement, one message at a time with each handler run to completion) and stateless services (load-balanced, local first). Handlers never wait: an ask's answer is mail, so actors that ask each other, in a chain or a cycle, always complete. (target, roadmap W6) A `[Durable]` request lands once per call id within its deadline whichever side crashes (ADR-082). | Cluster tests: single loaded actor per id across nodes, rebalance on join/leave without losing calls, service load balancing, chains and cycles of asks across nodes and through services (`CallChainTests`). |
| R5 | **Discovery and failure handling.** Nodes find each other through seeds and gossip; failed nodes are suspected and removed; graceful leave drains and unloads actors; a dropped node connection resumes without losing or repeating messages; a request whose caller already timed out is not run (on any node). Dispatch queues and mailboxes are bounded and refuse with `Overloaded`. | Cluster tests for join, crash (dead after timeout), graceful leave with in-flight calls, connections dropped mid-stream (`LinkTests`), expired requests (local and across nodes), full mailboxes. |
| R6 | **Messages + ECS.** `Ask` (request/response), `Send` (one-way) and `Publish` (every service type handling the message) without naming the receiver's type; per-tick logic in EasyEcs systems of the world. (target, roadmap W) `Publish` is deleted; pub/sub between actors is the optional `DaServer.Topics` (W6b, ADR-090). | Tests cover each delivery kind (`EventTests`); the sample uses `Ask` and `Send`. |
| R7 | **Clients.** Many client-facing nodes behind one well-known address (the platform's load balancer; old connections move to new nodes, `MaxConnectionAge`; target, roadmap W5: only a node above its group's average sheds its excess, ADR-089); client messages validated by `[FromClient]`; session-bound actor ids; pushes to a session or a group serialized once and fanned out per client-facing node; `SessionClosed` delivered to bound and granted actors, also when a client-facing node crashes. | Gateway tests: server-only messages refused, binding isolation, group broadcast across client-facing nodes, exact delivery under churn, connections moving to a node started later, `SessionClosed` on close and crash. |
| R8 | **Orchestration.** One Aspire AppHost runs the cluster locally (dashboard, OpenTelemetry) and publishes it (Docker Compose / Kubernetes). Node projects carry no names, ports or seeds. | `tests/DaServer.E2E` starts the AppHost with `Aspire.Hosting.Testing` in CI and passes only when the bot exits 0 (`E2E OK`). |
| R9 | **ECS all the way down.** Business code and the shard runtime follow EasyEcs's ECS principles: actors are entities (`ActorKey`), behaviour is stateless static handlers and systems, per-actor runtime state (lifecycle, mailbox, known sessions) is components and tags, per-shard state is singletons, each runtime system has one job, no event bus inside a world, no inheritance or virtual members in user code (ADR-081). | Design review against [EasyEcs ecs-principles](https://github.com/JasonXuDeveloper/EasyEcs/blob/master/doc/ecs-principles.md); no EECS warnings. |
| R10 | **Misuse is a build error.** Handler shapes (a static class, a static non-generic method, the message first, then only components, singletons, `Entity`, `World` and `Context`, no components in a service, the return type vs. the request's reply, no `async`, duplicates, accessibility), message shapes (struct, `[NinoType, Message]`, non-generic), types that cannot cross the wire, id collisions, messages used against their flow, actors, services and systems with fields, a session or group asked or addressed by a client, shared logic referencing the server, synchronous waits and work started on other threads in shard code, systems that ask, components declared beside logic, invalid persisted or handed-off components, `IPlaced` on a type that is not an actor id, a wire layout changed against its committed manifest or not recorded, a collection held directly by a client message, an actor disconnecting a session with `Send`, a misshapen `[Filter]`, a component parameter used after a structural change of its entity (DAS001-DAS022). | One generator test case per diagnostic; generators never report diagnostics themselves. |
| R11 | **Scale.** 10,000 players through 3 gateways to one game node, moving in one map (area of interest, dead reckoning) while the realm broadcasts to everyone every 5 ticks: no gap, no disconnect, p99 broadcast latency under 250 ms on a 4-core machine, servers allocate nothing in steady state. | `dotnet run --project samples/mmo/Sample.AppHost` (its bots: `--bots 10000 --seconds 60 --lean`, broadcast p99 limit 250 ms) ends with the bots exiting 0; node stats lines show 0 KB/s without OTLP. |

## 2. Engineering requirements

| # | Requirement | Acceptance |
|---|---|---|
| E1 | **Zero GC on hot paths** in steady state: calls, one-way messages, replies, events, pushes, broadcasts, mailbox, ECS ticks. | `AllocationTests` (process-wide counter, so background runtime work is included; any per-message allocation is >= 24 B; `BufferPool` growth to a new peak is pinned memory kept for reuse, counted apart and bounded): < 1 B per delivery for gateway fan-out; < 8 B per call/event across shards, across nodes and through a gateway to another node, per reply given later or after an ask, per delayed send, per checkpoint, per call of a 2,000-wide burst, per service message, per refusal (`Overloaded`, `NotHosted`, relayed `Timeout`) and per actor load and unload; an idle node allocates nothing per tick or wake. BenchmarkDotNet `Allocated` per operation reported for RPC, events and broadcast (only harness allocations allowed, explained). |
| E2 | **Latency and throughput** measured with BenchmarkDotNet over real loopback sockets. | RPC round trip (same node, cross node), concurrent calls, events, group broadcast to 1k/5k clients, broadcast to everyone through 3 gateways (3k/9k): numbers recorded in the README; no regression > 10% against the previous recorded run without an explanation. |
| E3 | **Bounded memory.** Every queue and buffer is bounded or pooled; slow consumers are disconnected; pools retain at most a configured budget. | Code review checklist; `BufferPool` and connection limits documented next to the code. |
| E4 | **Thread safety is explicit.** User code runs on shard threads only; cross-thread handoff only through the shard dispatch queue; shared runtime state is immutable snapshots. | Review: no locks in user-facing code paths; every shared structure documents its contract. |
| E5 | **Decoupled layers.** Business code sees `ICluster` (messages, pushes, groups), never `Node`. Dependencies point one way. (target, roadmap W2) Six packages (ADR-086): Core → Client \| DaServer (the runtime and the node host) → Persistence.PostgreSql; Testing references DaServer and Client; Aspire is AppHost-side and references only Core, no server assembly. | `ArchitectureTests.PackagesDependOnlyDownwards`; `Context.Cluster` and `world.Cluster` return `ICluster`. |
| E6 | **DRY and concise.** No copy-pasted variants (generated or shared helpers instead); no file over ~400 lines without a reason. | Review; `wc -l`. |
| E7 | **Incremental generator rules.** Syntax predicates first, equatable symbol-free models, tracking names, no diagnostics from generators. | `GeneratorTests.UnrelatedEditsHitTheCache` covers every syntax stage. |
| E8 | **Tests.** Unit, in-process cluster, gateway/client, generator/analyzer, allocation and end-to-end (AppHost + bots) tests; all green in CI on every push. | `dotnet test`: all pass; CI green. |
| E9 | **Docs.** README (what/why/how with mermaid), design, decisions (one ADR per non-obvious choice), roadmap, this file. Code, comments, commits and docs in English. | Review. |
| E10 | **Commits.** Logic, docs and CI in separate commits; author = repository owner, committer = signing identity (Verified); no session links. | GitHub shows Verified on every commit. |
| E11 | **Native AOT** (target, roadmap W8). Every node publishes with `PublishAot=true`: registration, dispatch and framework systems are generated as closed types in the user's assembly (no reflection, `MakeGenericType`, `Activator` or assembly scanning); serialization is Nino's generated formatters; the HTTP plane uses the slim builder and no JSON in the framework (admin endpoints as Nino or plain text; JSON only per endpoint through the application's source-generated context, ADR-083). Framework projects set `IsAotCompatible` on net11.0. JIT and AOT nodes change code the same way, by hot restart or rolling upgrade (ADR-084, ADR-088). | The trim and AOT analyzers run on every build (0 warnings); release checklist step 6. No suppression is accepted; EasyEcs 4.6 publishes without warnings with tracked components, so what remains to verify is the third-party packages ([drafts/architecture.md](drafts/architecture.md) section 8). |

## 3. Release checklist

Run in order; record results in the roadmap.

1. `dotnet build DaServer.slnx` — 0 warnings, 0 errors.
2. `dotnet test DaServer.slnx` — all pass (count recorded).
3. `grep -rn "Role\|\"game\"\|\"gateway\"" src samples` — topology strings only in the AppHost (and doc comments).
4. BenchmarkDotNet: `RpcBenchmark`, `MessageBenchmark`, `BroadcastBenchmark`, `ScenarioBenchmark` — mean and
   allocated recorded.
5. Sample end to end: the AppHost's 10k-bot scenario prints `E2E OK` (R11).
6. Native AOT (E11; target, roadmap W8): `dotnet publish -p:PublishAot=true` for each sample node with 0 warnings, and the E2E tests
   passing against the AOT binaries.
7. Review against R1–R11 and E1–E11 (this file); open items go to the roadmap.
8. CI green on the pushed branch; commits Verified.
